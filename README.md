# 28.kiji — 記事型アフィリエイトサイト（毎日自動更新）

普通のアフィリエイトサイトです。ランキング記事・個別レビュー・比較記事があり、
アフィリエイトリンクで収益化します。**料金の確認とサイトの再生成が毎日自動で走ります。**

[27.A8](../27.A8/) が「どの案件に申請するか」を決める道具なのに対して、
こちらは**読者に見せるサイトそのもの**です。

---

## 1. ASP を問わない

`config/offers.yaml` に案件を並べるだけです。A8 でも Zucks でも SmartC でも、
承認されたリンクを `affiliate_url` に貼れば同じ仕組みで記事になります。

成果タイプは5種類。記事の書き方と掲載順位に効きます。

| kind | 意味 | 例 |
|---|---|---|
| `download` | アプリ・ゲームのDLで成果 | ゲームDL案件 |
| `signup` | 無料登録で成果 | 会員登録 |
| `trial` | 無料体験で成果 | オンライン英会話 |
| `purchase` | 購入で成果 | 物販 |
| `click` | クリックで成果 | クリック報酬 |

> **ゲームDL案件について**: A8 の公開ランキングにはほぼ存在しません（実測で確認）。
> A8 の管理画面の全カタログか、Zucks・SmartC などアプリ特化ASPで探して、
> 承認されたものをここに書いてください。仕組み側はどのASPでも動きます。

## 2. 毎日自動で更新されるもの／されないもの

### 自動（毎日 JST 07:00 に GitHub Actions が実行）

- 各サービスの公式ページを取得して**変化を検出**
- 変わっていれば `/updates/` に日付つきで記録
- 「最終確認日」を全ページに反映
- サイト全体を再生成して GitHub Pages へデプロイ

### 手動（自動化していない）

- **実際に使ってみた評価**（`verdict`）
- **正確な料金**（`prices`）

この2つを自動化していないのには理由があります。

---

## 3. 料金は「人が書き写し、機械が変化を見張る」

最初は料金を全自動抽出する作りにしましたが、**実測で使い物になりませんでした**。

| サイト | 自動抽出の結果 | 実際 |
|---|---|---|
| ネイティブキャンプ | 6,800円 | 通常月額は 7,480円（年間割引価格を拾っていた） |
| DMM英会話 | 1円 | ページ内の別文脈の数字 |

通常価格と割引価格が併記されているページで、どちらがそのプランの料金かは
機械では断定できません。値引きフィルタを直すと、今度は全件「断定不能」になりました。

そこで分業にしています。

- **人**: 公式ページを見て料金を1度だけ正確に書き写す（`prices`）
- **機械**: 毎日ページを見て**変化を検出**し、`prices_checked` より後に変わっていたら
  サイトに「公式サイトの内容が変わっています。下の料金は古い可能性があります」と自動表示

機械に断定させて間違った料金を載せるより、この形の方が正確で、しかも
更新の手間はほとんど増えません（変わった時だけ通知が出る）。

料金がJavaScriptで描画されているサイト（実測: Cambly）は `watch.url` を空にします。
取れない値を推測で埋めることはしません。

## 4. 「試していないものは試していないと書く」を構造で強制

`verdict` が空の案件は:

- 記事に「**まだ試していません**」と明示され、使用感を一切書かない
- 掲載順位が **×0.25** されて下に落ちる（`UNVERIFIED_PENALTY`）

2026年3月のコアアップデートで最も強く叩かれたのが「使ってもいないものを
1位に置く記事」なので、順位のロジックそのもので防いでいます。
`/methodology/` に「掲載N件のうち実際に試したものはM件」と自動で出ます。

## 5. 構成

```
main.py                  パイプライン入口
├── src/fetch.py         robots.txt遵守・レート制限つきHTTPクライアント（27.A8から移植）
├── src/catalog.py       config の読み込みと検証
├── src/extract.py       ★料金抽出。断定できないものは confidence を下げて伏せる
├── src/track.py         ★履歴の蓄積と変化検出。signature 方式
├── src/articles.py      ★記事データの組み立てと掲載順位
├── src/render.py        Jinja2 で docs/ に書き出し
├── src/verify.py        生成物の検査（広告リンクの rel 抜けを落とす）
├── config/site.yaml     ★サイト名・公開URL
├── config/offers.yaml   ★ここに案件を並べる。運用で触るのはほぼこれだけ
├── data/prices.jsonl    ★料金履歴。絶対に消さないこと
└── docs/                生成物。Pages が配信する
```

## 6. 使い方

```bash
pip install -r requirements.txt
```

```bash
python main.py
```
本番。公式ページを確認 → 変化を履歴に記録 → サイト再生成。CIが毎日これを実行します。

```bash
python main.py --check      # 抽出が壊れていないか点検（履歴は汚さない）
python main.py --render     # 巡回せず既存の履歴からサイトだけ作り直す
python main.py --verify     # 生成済み docs/ を検査する
pytest tests/               # 回帰テスト
```

### 公開までの手順

1. `config/site.yaml` の `base_url` と `contact_url` を自分のものに書き換える
2. `config/offers.yaml` に案件を並べる（`affiliate_url` は承認後でよい）
3. GitHub リポジトリを作って push
4. Settings → Pages → Source を **GitHub Actions** にする

### 案件を1件足す手順

```yaml
- slug: my-offer
  name: サービス名
  kind: download          # ゲームDLならこれ
  category: ゲーム
  landing_url: https://...
  affiliate_url: ""       # 承認されたら貼る
  watch:
    url: https://...      # 料金ページ。取れないなら "" でよい
    labels: [プランA]
  prices:                 # 公式を見て書き写す
    - {label: プランA, amount: 1980}
  prices_checked: "2026-08-07"
  pitch: 一行の訴求
  points: [公表されている事実, ...]
  verdict: ""             # 実際に使ってから書く。空なら「未検証」表示
```

## 7. 収益についての但し書き

このシステムが保証するのは「料金が毎日確認され、変わった日が記録され、
サイトが自動で最新化されること」だけです。
検索流入が付くまで日本語圏でも3〜6ヶ月かかり、収入は保証しません。

伸ばすために効くのは、順に:

1. **提携を増やす**（`affiliate_url` が空だと収益はゼロ）— [27.A8](../27.A8/) の `--top` が候補を出します
2. **`verdict` を埋める**（実際に試す）— 順位が4倍になり、記事が読まれるようになる
3. 案件を増やす
